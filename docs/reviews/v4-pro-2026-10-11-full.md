## 1. Критично (баги, дыры в безопасности)

### 1.1. Пайплайн обрабатывает все файлы, а не новые
**Суть.**  
После успешного `ytdl.py` GUI запускает транскрибацию, пунктуацию и суммаризацию, передавая в команды корневую папку загрузок, а не список только что скачанных файлов.  
Это видно по сигнатурам `_build_transcribe_cmd()`, `_build_punctuate_cmd()`, `_build_summarize_cmd()` — они используют `download_dir`/`download_root`, а не конкретные пути.  
Каждый новый запуск приводит к повторной обработке всей коллекции.

**Зачем.**  
Пользователь запускает скачивание одного видео, а транскрибируются и суммаризируются все ранее скачанные файлы. Это часы лишней работы и расход API-токенов.

**Как чинить.**  
Добавить в `ytdl.py` вывод манифеста созданных файлов (JSON), затем GUI передаёт этот манифест следующему этапу. Или после скачивания вычислять свежие файлы по `mtime` и передавать их точечно.

**Оценка:** M.

### 1.2. Ошибка формирования имени выходного файла в `summarize.py`
**Суть.**  
```python
basename = path.name[:-len(".txt")]
output_path = path.with_name(f"{basename}{SUFFIX_OUTPUT}")
```
Для `video_punctuated.txt` даёт `video_punctuated_summary.md`, а ожидалось `video_summary.md`.  
Причина: не снимается суффикс `_punctuated`.

**Зачем.**  
Имена файлов не соответствуют ожиданиям пользователя, усложняют поиск, ломают конвенции.

**Как чинить.**  
```python
basename = path.name.removesuffix("_punctuated.txt")
# или
basename = path.stem.removesuffix("_punctuated")
```

**Оценка:** S.

### 1.3. `TypeError` при сортировке видео канала
**Суть.**  
В `get_channel_videos`:
```python
entries.sort(key=lambda x: x.get("view_count", 0), reverse=True)
```
Если у записи есть ключ `view_count` со значением `None` (не удалось получить просмотры), сравнение `None` и `int` вызовет `TypeError`.  
Аналогично для `upload_date`:
```python
entries.sort(key=lambda x: x.get("upload_date", ""), reverse=True)
```
`None` и `str` не сравниваются.

**Зачем.**  
Падение скрипта при обработке каналов с неполными метаданными.

**Как чинить.**  
Использовать `(x.get("view_count") or 0)` и `(x.get("upload_date") or "")`.

**Оценка:** S.

---

### 1.4. Падение на невалидных записях плейлиста/канала
**Суть.**  
В `download_playlist`:
```python
for entry in entries:
    video_url = f"https://www.youtube.com/watch?v={entry['id']}"
```
`--ignore-errors` может вернуть `entries`, содержащие `None` или объекты без `id`, что приводит к `TypeError: 'NoneType' object is not subscriptable` или `KeyError`.

Аналогично в `get_channel_videos`:
```python
video_url = f"https://www.youtube.com/watch?v={entry['id']}"
```

**Зачем.**  
На реальных плейлистах часто встречаются недоступные видео; скрипт должен их пропускать, а не падать.

**Как чинить.**  
Перед обработкой фильтровать: `entries = [e for e in entries if isinstance(e, dict) and e.get("id")]`.

**Оценка:** S.

### 1.5. Не проверяется существование `transcribe_python` из `config.yaml`
**Суть.**  
`config.yaml` содержит:
```yaml
transcribe_python: /home/ypc/projects/05_Transcribe/venv/bin/python
```
GUI читает этот путь через `_read_transcribe_python()` и использует для запуска транскрибации. Если путь не существует, процесс падает уже после успешного скачивания.

**Зачем.**  
Путь жёстко привязан к машине разработчика. На другой машине пайплайн остановится после скачивания.

**Как чинить.**  
Проверять `os.path.exists(path)`; если нет — fallback на `sys.executable` или интерпретатор текущего venv.

**Оценка:** S.

### 1.6. Полная зависимость `requirements.txt` не покрывает транскрибацию и пунктуацию
**Суть.**  
В `requirements.txt` только:
```
yt-dlp>=2024.12.0
tqdm>=4.65.0
pyyaml>=6.0
```
Но:
- `transcribe.py` импортирует `vosk`;
- `punctuate.py` импортирует `punctuators`;

- `punctuate.py` опционально использует `colorama`.

**Зачем.**  
Проект невозможно развернуть по инструкции `pip install -r requirements.txt`.

**Как чинить.**  
Добавить `vosk`, `punctuators`, `colorama`, либо вынести ML-зависимости в отдельный `requirements-ml.txt` и прописать в `run.sh`/документации.

**Оценка:** S (по времени), но критично для запуска.

### 1.7. Утечка секретов через `secret_conf.yaml` и `cookies.txt`
**Суть.**  
`summarize.py` читает API-ключ из `secret_conf.yaml` в корне проекта. В дереве проекта его нет, но код предполагает его наличие. Если файл добавить в git — ключ утечёт.

**Зачем.**  
Компрометация ключа API и YouTube-аккаунта.

**Как чинить.**

- Использовать переменные окружения (`DEEPSEEK_API_KEY`) как основной способ.
- Хранить ключ за пределами репозитория (например `~/.config/project/secret.yaml`).

**Оценка:** S.

## 2. Архитектура и структура

### 2.1. Распределённое управление конфигурацией
**Суть.**  
Конфиг `config.yaml` читается вручную в трёх местах:
- `ytdl.py` — ручной парсинг строк;
- `gui.py` — `_read_download_root()`, `_read_transcribe_python()` — тоже вручную;
- `run.sh` — через вызов `python3 -c ...`.

**Зачем.**  
Дублирование, рассинхрон форматов, ошибки при появлении новых ключей.

**Как чинить.**  
Создать единый модуль `config.py` с функцией `load_config()` на основе `yaml.safe_load` и обращением из всех скриптов. GUI переписать на этот модуль.

**Оценка:** M.

---

### 2.2. Жёсткая цепочка этапов в GUI
**Суть.**  
В `_on_process_finished()` последовательность `ytdl → transcribe → punctuate → summarize` задана набором `if`:
```python
if self.stage == "ytdl" and rc == 0 and self._transcribe_requested:
    ...
if self.stage == "transcribe" and rc == 0:
    ...
if self.stage == "punctuate" and rc == 0:
    ...
```
Добавление нового этапа или условного пропуска требует правки этого метода.

**Зачем.**  
Хрупкость, сложно тестировать, невозможно переиспользовать в CLI.

**Как чинить.**  
Выделить пайплайн в отдельный класс `Pipeline` с этапами (`Stage`), передачей результата между этапами и состоянием. GUI только отображает прогресс и запускает/останавливает.

**Оценка:** L.

---

### 2.3. Дублирование игнорируемых путей и поиска файлов
**Суть.**  
`DEFAULT_IGNORE_DIRS`, `DEFAULT_IGNORE_FILES`, `DEFAULT_IGNORE_EXTENSIONS` почти полностью скопированы в `transcribe.py` и `punctuate.py`. Логика `find_text_files` / сбора аудиофайлов также дублируется.

**Зачем.**  
Изменения в одном месте не отражаются в другом, риск рассинхрона.

**Как чинить.**  
Вынести общий модуль `filesystem.py` с функциями `iter_files`, `should_ignore`, константами. Оба скрипта импортируют его.

**Оценка:** M.

---

### 2.4. Глобальные константы и состояние в `ytdl.py`
**Суть.**  
`DOWNLOAD_ROOT`, `INPUT_FILE`, `LOG_FILE` — глобальные переменные, изменяемые после чтения конфига. Функции принимают их неявно из замыкания.

**Зачем.**  
Плохая тестируемость, невозможность переиспользовать функции с другими путями.

**Как чинить.**  
Собрать настройки в dataclass `AppConfig`. Передавать конфиг явно в функции или сделать `ytdl.py` классом.

**Оценка:** L.

---

### 2.5. Разделение ответственности в `transcribe.py` и `punctuate.py`
**Суть.**  
`AudioTranscriber` и модуль пунктуации одновременно отвечают за:
- чтение конфигурации,
- поиск файлов,
- загрузку модели,
- обработку одного файла,
- вывод статистики.

**Зачем.**  
Модуль сложно тестировать изолированно, высокая связность.

**Как чинить.**  
Разбить на классы: `FileFinder`, `ModelWrapper`, `Processor`. Основной скрипт только связывает их.

**Оценка:** M.

---

### 2.6. Пайплайн через `subprocess` вместо программного вызова
**Суть.**  
GUI запускает скрипты как отдельные процессы. Это даёт изоляцию зависимостей, но теряется передача структурированных данных: только stdout-строки.

**Зачем.**  
Невозможно передать список новых файлов, состояние, ошибки в структурированном виде.

**Как чинить.**  
Оставить subprocess для изоляции, но передавать между этапами JSON-манифест временного файла или через stdin/stdout. Либо импортировать функции, если зависимости позволяют.

**Оценка:** M.

## 3. Читаемость и поддерживаемость

### 3.1. Операторный приоритет в `is_playlist_url`
**Суть.**  
```python
return "list=" in url and "shorts" not in url or "/playlist?" in url
```
Читается неочевидно. Смешивание `and`/`or` без скобок — источник ошибок.

**Как чинить.**  
```python
return ("list=" in url and "shorts" not in url) or "/playlist?" in url
```

**Оценка:** S.

---

### 3.2. Магические строки и ручные операции с путями
**Суть.**  
В `summarize.py`, `transcribe.py`, `punctuate.py` много `suffix`, `prefix`, конкатенаций строк.  
Пример:
```python
basename = path.name[:-len(".txt")]
```
Вместо `Path.stem`.

**Как чинить.**  
Использовать `pathlib` везде: `Path.with_suffix()`, `Path.stem`, `Path.with_name()`.

**Оценка:** S.

В `download_single_video`:

```python
import yt_dlp

import logging
```

**Как чинить.**  
Вынести импорты в начало файла.

**Оценка:** S.

### 3.4. Запутанная логика временных WAV в `transcribe_file`

Множественные вложенные проверки `wav`, конвертации и временные файлы (`temp_wav`, `temp_wav2`) с ручной очисткой в `finally`. Код тяжело читать и легко сломать.

## 5. Производительность

### 5.1. Последовательная обработка LLM-файлов
**Суть.**  
`summarize.py` обрабатывает файлы строго по одному, без параллелизма.

**Зачем.**  
Для десятков файлов это очень медленно. API DeepSeek позволяет несколько одновременных запросов.

**Как чинить.**  
Использовать `concurrent.futures.ThreadPoolExecutor` с ограничением (например 4 потока) и аккуратной обработкой rate limit.

**Оценка:** M.

---

### 5.2. Транскрибация без батчинга
**Суть.**  
`transcribe.py` обрабатывает файлы последовательно, конвертация через ffmpeg по одному.

**Зачем.**  
На многоядерных машинах можно параллелить конвертацию и распознавание.

**Как чинить.**  
Параллелить на уровне файлов (несколько воркеров). Но аккуратно с памятью: Vosk-модель одна на процесс.

**Оценка:** M-L.

---

### 5.3. Пунктуация без батчинга модели
**Суть.**  
`punctuate.py` вызывает `model.infer([text])` для каждого файла отдельно.

**Зачем.**  
Модель ONNX может эффективно обрабатывать батчи, снижая накладные расходы.

**Как чинить.**  
Накапливать тексты и подавать батчами (с учётом памяти). Либо хотя бы использовать многопоточность, если модель потокобезопасна.

**Оценка:** M.

---

### 5.4. Повторное сканирование всех файлов после скачивания
**Суть.**  
Как следствие бага 1.1, транскрибация/пунктуация сканируют всю папку, что даёт O(N) на каждый запуск.

**Зачем.**  
Устранить повторную обработку — это одновременно и производительность, и корректность.

**Оценка:** входит в 1.1.

---

### 5.5. Verbose-вывод в транскрибации
**Суть.**  
Печать каждой фразы:
```python
print(f"    > {text}")
```
При большом файле создаёт тысячи строк в stdout.

**Зачем.**  
Замедляет вывод, засоряет лог.

**Как чинить.**  
Снизить уровень логирования или выводить прогресс через `tqdm`.

**Оценка:** S.
